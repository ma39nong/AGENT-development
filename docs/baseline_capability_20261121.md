# Baseline：完整视频、历史输入与Prompt切换能力筛查

日期：2026-11-21。结论：当前配置未通过自动计数与任务切换筛查；未开始LoRA，未控制机器人。

## 本轮问题与范围

先测现有baseline是否能从原始视频理解粗阶段和颗数，再测只看截至当前的过去视频，能否为“摘四颗，必要时调整”和“先两颗→调整→再两颗”请求不同Prompt。不是新增细阶段标注项目，不要求用户实时看每次输出。

本地baseline明确为Qwen3-VL-4B-Instruct；云端qwen3.8-max仅作能力对照，不能把它的结果当成本地能力。1条train录像，多条件筛查，不是独立多录像准确率。

本地完整视频2次，三种历史输入各6次，共20次本地推理。云端正式历史矩阵18次，另有1次补充执行时间线对照。早期512输出预算造成的截断诊断另存max-stream，不混入正式结果；该目录保存7条诊断记录，另有终止时可能在途请求，不能据文件数推断全部计费次数。

## 原始视频与时间

完整输入保留原始MP4及源SHA，不客户端拼图或拆成多图消息。本地使用Transformers原生video输入、官方视频处理器和OpenCV解码，模型内部2fps采样且保留源帧索引/FPS；云端video_url处理内部采样未实测。不能把原文件提交等同于模型逐帧读全部30fps。

在线回放只含截止时刻前帧，测试截止点为27、37、47、62、77、86秒。每个片段保留原30fps和原尺寸，H264 CRF18重编码，非原文件字节；源帧范围和SHA在manifest中，逐片核对FPS及帧数。第一版编码被检测出帧钟变化，第二版参数不兼容，均未作为推理输入；正式矩阵只使用clips-v3。

输出可格式化为26.00s，但两位小数不是0.01秒识别精度。原视频30fps、本地内部2fps，必须另外测边界误差/可确认区间；本轮不宣称百分之一秒精度。

## 三种历史输入

- recent_only：只给新到达的连续视频片段，不给此前计数。
- recent_memory：新片段加此前模型生成的事件时间记录，不填入人工正确数量。未知、矛盾和结构拒绝会使记忆完整性标志失效。
- prefix：截至当前的完整过去视频；每次重看全部过去，不给未来帧。

三种模式都说明当前执行Prompt与调整是否完成，这是执行器提供的已知状态，不是盲阶段识别评测。原视频只在本轮离线回放中继续播放，不会按Agent的请求改变轨迹。wait仅表示未请求新Prompt，不代表底层动作已停止，更不能作为可靠暂停能力。

| 模型/输入 | 六个检查点的累计计数 | 耗时中位数 |

| local/recent_only | 未知/未知/未知/未知/未知/未知 | 1.66秒 |

开发端参考累计数为1/2/3/3/4/5。全部是同一录像的相关检查点，不能将6次对上称作独立样本准确率100%。近期片段缺历史时返回未知是合理的，不应当作视觉判断错误。

本地18次都没有确认成功事件，均给未知/等待，尚无法用该配置可靠积累记忆。Max的完整过去视频能在六个点数对累计数；近期片段加文字事件在前四个点数对，77秒和86秒仍返回总数未知，出现事件账本已增加但理由又说未确认的矛盾。

## 两个任务的实际决定与时效

- 2+2：Max的prefix在37秒数到2并请求adjust，符合该时刻的目标触发；本次完整耗时6.37秒，下界返回时刻约43.37秒。原录像40秒已可确认第三颗摘离，故该次决定返回时已经晚于第三颗摘离。
- 总目标4：prefix在77秒数到4并请求return；本次耗时10.65秒，下界返回时刻约87.65秒。原录像81秒已可确认第五颗摘离，故不能称为及时阻止第五颗。
- 这些源帧时刻是粗视觉参考，不是实机不可撤销动作的精确截止时间；视频编码/采样等待/机器人交接尚未全部计入。本轮已经能看出响应落后，不能由异步线程消除这段语义延迟。

## 顺序约束问题与自动检查

录像实际为前三颗后调整，再继续摘。Max在77秒把26、36、45、76秒四个事件认作满足2+2，实际45秒第三颗发生在46.9秒调整之前，属于3+1。

先前仅给executor_adjustment_completed布尔不足以表达先后关系，因此补测了执行切换时间线（46.9秒adjust生效、61.267秒回到harvest；本轮由subtask模拟，不是实机回执）。Max仍把45秒事件说成在调整之后，错误地宣称2+2满足。

prompt_plan_guard.py用候选事件和执行回执时间检查数量/用户顺序。当前可自动拒绝这个3+1完成声明；数量取自任务参数，单元测试覆盖4颗无调整、2+2、3+2等逻辑，不固定默认两轮。通过约束检查只代表逻辑一致，视觉事件本身仍可能误判，不授予动作执行权限。

原录像不会响应37秒提出的提前调整，也没有“连续摘四颗后直接放回”的真实路径，所以两条新路线的实机成功率尚未验证。条件逻辑单元测试不等于真实视觉或机器人成功。

## 当前选定的后续结构

近期真实视频负责判断当前持果/释放等情况；结构化事件记忆负责累计、未知和去重；实际Prompt切换回执负责先后顺序；关键视觉片段供查询复核。Qwen提出选择，程序核验用户约束与执行能力。不要求人工每次批准，也不让错误结构或迟到决定直接控制机器人。

完整历史回看可作离线基线与异常复核，不先假定持续攒整段视频是可用的在线方案。先修正/验证本地视觉基线、记忆和决定一致性，再决定小规模LoRA针对哪些错误；不能用重标204条细阶段作为前置条件。

达到计数目标后是否及时切换，需要对每次采摘前的放行机制和真实执行能力继续验证。未证实保持/暂停可用，不能只输出wait就认为不会多摘。

## 自动运行与复现

脚本按批次生成原回答、结构拒绝、候选记忆与时效记录，不需要用户盯每次请求；本轮没有创建定时任务或后台长期监控。

```bash
.venv/bin/python scripts/local_video_baseline.py --jobs runs/baseline-capability-v1/local-jobs.json --output runs/NEW-local-full
.venv/bin/python scripts/streaming_capability.py run --backend local --manifest runs/baseline-capability-v1/clips-v3/manifest.json --output runs/NEW-local-stream
.venv/bin/python scripts/streaming_capability.py run --backend api --manifest runs/baseline-capability-v1/clips-v3/manifest.json --output runs/NEW-max-stream
.venv/bin/python scripts/report_capability.py --root runs/baseline-capability-v1 --reference data/capability_reference_debug_v1.json --output docs/baseline_capability_20261121_summary.json
```

参考计数仅供report脚本评估，不进入模型问题；原始录像、派生视频、密钥与权重不提交Git。机器报告见[汇总](baseline_capability_20261121_summary.json)。27项单元测试与Ruff F/E9通过；这是契约/逻辑测试，不是实机验收。
