# 固定 Max 案例的延迟工程验证

用户要求在既定 Max＋严格短输出＋完成条件＋交接门控路线内提速。只使用已有固定案例，未扫模型、提示词或扩大视频集；本轮20次付费调用（12＋8），无重试，门控和真实控制均未改变。结果没有证明稳定加速，因此没有把候选传输/分段方案替换为已验证部署默认。

## 原22次完成条件实验中的线索

输出仅21～31 token，不能把剩余秒级耗时主要归因于答案太长。原连续前缀输入约2480～30390个video_tokens；第一次请求缓存字段为0，第二次多数命中，但冷/暖顺序、负载、答案长度不同，不能把所有改善归因于缓存。尤其后续实验中缓存命中约3万个token仍有10秒请求，缓存不是延迟保证。

## 一：连接复用，12次固定对照

B1前、B2前、B4后三个已有案例，每个按fresh / session / session / fresh调用。两条件都用同一Requests后端、相同环境代理和TLS验证；每案例payload SHA相同，保留原视频和提示词。无重试/重定向，完整读取响应后才复用连接。通过套接字指纹确认6次session请求复用了同一连接；未记录代理URL或认证内容。

整体fresh中位2.901秒、session中位2.362秒，**不能直接据此宣称提速18.6%**：每组第一次control更慢，缓存命中和调用顺序并未完全控制。与同案例最后一次fresh相比：

| 案例 | 最后一次fresh | 中间两次session中位数 |
| --- | ---: | ---: |
| B1前 | 1.495秒 | 1.578秒 |
| B2前 | 2.408秒 | 2.362秒 |
| B4后 | 2.910秒 | 3.048秒 |

没有稳定优势。B4后首次fresh已命中30720个token，仍耗10.287秒；后续同缓存命中只需约3秒，不能只解释为缓存差异。等待响应头占几乎全部耗时，响应头之后读取完整小JSON约0.1毫秒，但响应头等待同时包含连接、代理、上传与服务端处理，**无法据此单独归因服务端排队或prefill**。

结果：12/12严格结构有效，同案例四次答复一致；一致不等于完成证据正确。

## 二：固定历史段＋新增段，8次固定对照

只用B4前/后两个原案例。同一持久连接、Max、系统提示词、JSON模式、输出上限与任务上下文，按full / segmented / segmented / full调用。分段附必要的原任务时间范围，属于视频打包及对应时间说明整体变化；不能解释成纯粹某个缓存开关的因果试验。

将原始因果前缀按关键帧复制拆分为0～61秒的固定历史与61秒之后的新段，不重新编码、不丢掉历史画面。逐帧解码SHA序列验证拆分前后完全相同；两个观测共享同一不可变历史视频文件。最初容器元数据虽不同而像素一致，预检中止，0次API调用；v2复用经过逐帧验证的同一历史文件后完整执行。

| 打包方式 | 次数 | 完整响应中位数 | 最慢 |
| --- | ---: | ---: | ---: |
| 单一完整前缀 | 4 | 2.905秒 | 9.837秒 |
| 历史段＋新增段 | 4 | 4.593秒 | 6.179秒 |

B4后第一次分段调用命中15360个历史token，但耗6.048秒；同观测的第二次分段全量暖缓存约2.630秒，最后完整前缀约2.717秒。**稳定历史缓存复用可观察，但本批没有总体提速证据**。不能因最慢值下降就声称尾延迟解决，更不能从8次估计稳定P95/P99。

Base64仍上传全部片段字节，没有使用远程对象存储或服务端文件ID，故本次不证明减少上传流量；客户端保存视频不等于云端自动记住视频。视频Token因分段预处理略有差异，虽图像解码帧相同，也不能假定模型内部表示逐token相同。

8/8严格结构有效，与原案例给出相同交接提议。此前已经发现的过期状态判断与未核实的完成条件仍未解决；未将它们算作视觉验收通过。

## 收敛后的提速方向与边界

1. 不继续压已经只有几十token的输出；保留唯一Max和既定技能条件，先完成固定反例的正确性复核。
2. 优先验证按当前技能选择必要视频证据，并保留可检索的真实视频历史，而非每次云端从0秒重新审视全部任务。不直接回到无视觉历史的八秒窗口，也不在未验收前删掉释放、持稳或掉落等关键证据。本轮尚未测试这项输入选择，因此没有声称已获得收益。
3. 若需要保证秒级最慢等待，必须单独定位现有代理/线路和服务端处理，必要时取得服务端延迟保障；当前只有端到端API测量，没有遥测能支持更具体的归因。
4. 可以提前准备下一技能的条件分支，但最后是否完成仍需真实证据；异步/提前规划/交接等待都不能冒充视觉确认提速。未确认、过期、版本不匹配继续阻断；等待期间不能放任旧技能发起新采摘。

没有设定未经实机时序验证的性能承诺。2秒仍只是此前离线筛查阈值，真实截止时间需要动作执行回执决定。没有新增广泛付费批次、模型/提示词搜索或机器人操作。

参考机制：Requests Session支持连接池复用，见[官方文档](https://requests.readthedocs.io/en/latest/user/advanced/#keep-alive)；上下文缓存机制见[Model Studio文档](https://docs.modelstudio.console.alibabacloud.com/en/model-studio/context-cache)。当前端点的效果以上述实际测量为准，不以文档代替此路由的性能保证。
